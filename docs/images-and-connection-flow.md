# Safe image attachments and first connection

Built on `f6f3847` in `feat/embedded-tailscale`. Upstream was checked before this
work; `openma-ai/pi-bot main@7c78b35` had no newer changes. Existing direct and
embedded networking, normal file attachments, saved profiles and history remain.

## Image support

Static PNG, JPEG and WebP are validated from bytes, not their extension. The
pinned `image-size@2.0.4` parser reads dimensions; the host additionally checks
raster signatures/MIME consistency, bounded PNG/WebP chunks, complete PNG/JPEG
end markers, and rejects animated PNG/WebP. Maximum: 5 MiB, 8192 pixels per edge,
16,777,216 total pixels. Four attachments per message remains the file-protocol
limit. PNG/JPEG/WebP generated by the agent use the same checks on publication.
The parser validates headers/bounds; it is not a complete raster decoder.
Malformed image data can still fail browser/provider decoding and is reported.

Other file types keep ordinary file handling. SVG/HTML/HEIC/GIF are not inlined,
previewed, or treated as model image input. A missing safe-image descriptor is
shown as a file, including when connected to an older runtime; upgrade the
runtime for image validation and image-aware publication. No arbitrary local
path becomes a client image URL.

Image cards lazily fetch verified bytes through the existing authenticated,
scoped chunk protocol, recheck SHA-256, then construct a Blob with one of the
three allowed raster MIME types. No remote Markdown image URLs or raw HTML are
rendered. Previews revoke object URLs and cancel unfinished fetches off screen
or on unmount. The modal supports enlarged viewing, Escape, a close button and
focus return; original download uses the existing save/share path. Previews use
bounded original pixels displayed at thumbnail size, not a server-side resized
thumbnail service. Browser decode failures keep the ordinary file action.

## Real model input and honest fallback

`attachmentImages` checks the **current** Pi session model's declared `input`
capability. Supported models receive actual `{type:"image", data:<base64>,
mimeType:...}` parts through the installed Pi SDK's `prompt(...,{images})` and
`steer(...,images)` interfaces. Metadata/paths alone are not called vision.
The attachment content is explicitly untrusted data, never new authorization.

Text-only models receive no new image parts; both the model prompt and message
card explicitly report that the image was not supplied for vision, and instruct
the model not to claim it saw the image. The file remains downloadable. Users
can switch to a vision model and resend it.

Existing verified provider image budgets are preserved. Other models declaring
vision receive an explicit conservative **application** reservation of 65,536
context tokens per image, at most the model's declared request image count or
64, and 5 MiB per image. This is not a provider billing estimate or a promise
that every provider accepts every valid image. Long/image-heavy histories or
small model windows may be rejected by the existing context guard; images and
history are never silently dropped to make them fit. Real provider acceptance,
recognition quality, EXIF rotation behavior and model switching with old image
history have not been exercised against a paid model.

## First-run / reconnect flow

Disconnected managed clients now show a dedicated connection screen instead of
an apparently usable chat composer. A successful connection mounts the existing
conversation shell. The design reuses the project's dark Radix/amber primitives.

1. Choose location: “这台 Mac” (desktop default), “远程电脑” (phone default), or
   optional “通过 Tailscale”. No local option appears on remote-only clients.
2. Enter necessary existing-service configuration, credentials and (if selected)
   application authorization. Service/project directories are visible rather
   than hidden behind Advanced. Existing SSH trust checks remain mandatory.
3. Show connecting/cancel, a classified failure with retry/edit/back actions,
   then enter the conversation after success. No remote service is started.

Saved valid profiles appear as one-click reconnect choices. The last successful
profile is prioritized; no unsolicited automatic Tailnet login occurs. The
original default placeholder is omitted from reconnect choices without deleting
or changing saved records. The complete connection manager stays reachable.

Application network state is read-only (`notPrepared`, `prepared`, `dialed`,
`stopped`, or unavailable). `dialed` means a dial succeeded in this process,
not a perpetual health assertion. UI copy distinguishes application
preparation/authorization, unknown remote computer network login, SSH credentials
or host-key issues, and a missing/unreachable runtime. It never claims the cloud
computer is logged in merely because the client key was prepared. Outer VPN
routing remains relevant; no system VPN/proxy changes were made.

## Verification and evidence

Only local mocks, disposable localhost runtimes, a local faux model provider and
small generated 64×48 PNG/JPEG/WebP fixtures were used. No real photos, paid model,
Tailnet login, deployment, TestFlight upload or phone installation was used.

- 59 relevant JS/context/protocol tests pass: safe raster validation, malicious
  type/MIME/dimension/size rejection, real Pi session image parts for vision,
  zero image parts and explicit fallback for text-only, `publish_file` returning
  a PNG descriptor with exact bytes, file identity/scope and prior regressions.
- 10 native tests and one explicit offline userspace/SSH test pass, including
  prepared → dialed → stopped/empty node-state reporting without a real node.
- Real browser components were checked at 1280×850 and 390×844, and the phone form
  at 390×500 (keyboard-height emulation). Focused input remained visible with no
  horizontal overflow. Radio/Tab navigation, cancel/edit/retry, and modal Escape
  with focus return were exercised.
- A saved-profile success case entered the actual conversation shell against a
  disposable authenticated runtime. Image cards decoded a PNG Blob at 64×48;
  enlarged preview and original download were checked using synthetic bytes.
- Screenshots and logs: `artifacts/images-landing/` (ignored local evidence).
- Local Mac preview app and unsigned iOS archive builds are refreshed for this
  implementation. These are builds, not physical-device UI validation.

Remaining unverified: physical iPhone/iPad picker/keyboard/Save to Files/sharing,
real provider image interpretation, real Tailnet/VPN coexistence and physical
background/foreground recovery. iOS share remains compiled/linked support, not
a claim of an external share having completed.

The optional 21st component search returned HTTP 401. External `21st review` of
the new source files was denied by automatic approval review because it could
disclose source to an unverified service. It was not retried or bypassed; local
type/tests/browser inspection provided the review instead.

The reproducible local UI fixture is in `clients/tauri/test/ui/` with launch
instructions and first-run/returning/success/error/image URLs in its README.
The synthetic browser download's SHA-256 matched the PNG fixture exactly:
`d5dba6f6d47b60ca377c51b1730e7930b3ea68af156b1010e2edcadbb9752f93`.
